## Architecture this session established — read before writing a new converter

1. **Research the real plugin source first, never guess.** `references/animation-addons-for-elementor.4.2.2.zip` is the actual downloaded plugin (matching the codebase's existing convention: `essential-addons-for-elementor-lite.6.6.7.zip`, `header-footer-elementor.2.8.8.zip`). Extract it to a scratch dir and read the real widget PHP (`widgets/<slug>.php`) for exact control names before writing a converter — guessed names have silently dropped content before (`tests/AddonSettingNamesTest.php` exists because of exactly that failure mode).
2. **Check for reuse before writing a new class.** Many widgets in this suite turn out to use the *exact same* settings keys as a widget we already convert (native Elementor, EAEL, or HFE) — sometimes identical, sometimes needing one fallback key added (`$settings['x'] ?? $settings['wcf_x'] ?? ''`). About half of the 25 done so far needed zero or one new line, not a new class. Only build a dedicated `Wcf*Converter` class when the settings shape is genuinely different.
3. **`divi/group-carousel` + `divi/group`, not `divi/slider`, for anything that can show several items side by side.** `divi/slider` (childrenName `divi/slide`) only ever shows one full slide at a time. `divi/group-carousel`'s `module.advanced.slidesToShow`/`slidesToScroll`/`centerMode` natively support several visible items; its child, `divi/group`, is a free-form container (`childrenName: []`) so you build each item's content as ordinary child blocks (`divi/image`, `divi/heading`, `divi/text`, or `divi/testimonial` for testimonial carousels) rather than through fixed slide fields. `divi/slider` is still correct for Elementor's own native "Slides" widget (one full slide at a time by design).
4. **Reuse `BaseElementorConverter::groupCarouselModuleSettings( $settings )`** for the `module.advanced`/`arrows`/`dotNav` mapping — most of this addon's carousel widgets (`brand-slider`, `category-slider`, `content-slider`, `event-slider`, `filterable-slider`, `image-box-slider`, `advanced-testimonial`, …) share one internal trait, `Aaeaddon_Slider_Trait::register_slider_controls()` (`inc/Aaeaddon_Slider_Trait.php` in the reference zip), with identical control names: `slides_to_show`, `autoplay` (`'yes'`/`'no'`, default `'no'`), `navigation`/`pagination` (SWITCHER, `=== 'yes'` when on, absent/empty when off — not a `!== ''` check), `space_between`. A widget's own extra controls (e.g. `image-box-slider`'s `center_slide`) stay in that converter's own mapping.
5. **The `aae_`/`wcf_`/`brandberry_`/`bb_` prefixes and a few bare keys (`spin_text_*`, `_title`, `text_transform_origin`) are suppressed globally** in `BaseElementorConverter::logUnmappedSettings()`'s `$always_ignore_prefixes`/`$always_ignore` — cosmetic scroll-animation/parallax/tooltip settings this suite (and the Brandberry theme it ships with) attaches to *ordinary* widgets, present on nearly every element of a real export. Don't re-add per-converter suppression for these; do add a widget's own *other* style-only keys (colors, typography group-controls, padding) to that converter's own `logUnmappedSettings()` call — every new widget test should assert `$result['report']['skipped_settings'] === []`.
6. **Real, previously-uncovered bugs this session found and fixed, worth knowing about:**
   - `CountdownConverter` (native `countdown` widget) wrote to `module.advanced.countdownDate`, which `fixtures/divi-schema/modules.json` shows is not a declared attribute of `divi/countdown-timer` at all — the timer sat frozen at zero on every converted page, for every user, until now. Fixed to use `content.advanced.dateTime` (what `EaelCountdownConverter` already did correctly, with a comment describing this exact bug — the native converter was never fixed to match).
   - `is_string( $x['key'] ?? '' ) ? $x['key'] : ''` is **not** null-safe: `is_string('')` is `true`, so the ternary's true branch runs even when the key is missing and reads `$x['key']` with no fallback at all, triggering an undefined-array-key warning (and often a wrong `null` value). Use `?? null` for the `is_string()` check specifically: `is_string( $x['key'] ?? null ) ? $x['key'] : ''`. This bit 9 separate call sites across 6 files before being caught (first by the Docker probe's PHP warning output, later by `--display-warnings`); grep for the `?? ''` variant before trusting any code that looks like this pattern.
   - `ImageConverter` didn't handle a `link` setting at all (a real gap, not addon-specific — benefits the native Elementor "Image" widget too). `divi/image` reads its link from `image.innerContent.linkUrl`/`linkTarget` (`elementType: "imageLink"` in the module schema), **not** `module.advanced.link` the way `HeadingConverter`/`ButtonConverter` do it — check the module schema before assuming a pattern from one module applies to another.

## Workflow per widget (what's worked well)

1. Extract the reference zip if not already extracted (`unzip -oq references/animation-addons-for-elementor.4.2.2.zip -d /tmp/aae-inspect`), read `widgets/<slug>.php`'s `register_controls()` for real key names, and its shared trait if it `use`s one.
2. Check if an existing converter already reads the same or fallback-compatible keys (`grep -rn "settings\['" plugin/.../handlers/` for the candidate target). Prefer a one-line fallback over a new class.
3. Register in `ConverterRegistry::registerDefaults()` under the widget's real slug (`wcf--…`/`aae--…`, confirmed via `get_name()` in the widget source, not guessed).
4. Write a PHPUnit test asserting real structure *and* `$result['report']['skipped_settings'] === []`, in a new `tests/AnimationAddonsBatchN Test.php` or appended to an existing one.
5. Run the full suite with `--display-warnings`.
6. Verify against the real plugin via `tools/aae-probe/` for at least one representative case per batch (not necessarily every single widget — batching 3-8 widgets per verification pass has been the working cadence).
7. Commit with a message that cites the real source file(s) verified against, matching this session's commit style (see `git log` on this branch for examples) — the next session should be able to trust a commit message's claims without re-deriving them.
8. Push to `origin/fix/correctness-pass-2026-08`. Do not merge to `main` without asking — the user has explicitly said it can wait.
